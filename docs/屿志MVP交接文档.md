# 屿志 · 一座由你的日子长成的岛

概念与 MVP 交接文档（给 Claude Code）

---

## 1. 一句话定位

屿志是一个个人效率平台。你的工作和生活会自动长成一座等距视角的小岛：你负责定规则和做选择，小岛负责记账、提醒和讲故事。

它是一个**独立产品**，不是流动日历的一部分。

## 2. 来源：禾境

屿志的骨架来自之前做的微型文明模拟应用「禾境 · 一座生长中的微型文明」（单文件 `hejing.html`，请放在项目的 `reference/` 目录里参考）。

禾境里可以直接复用或改造的部分：

- 等距视角的小岛地图、地块绘制、季节改变地表颜色
- 小人在地图上寻路、去不同地点干活
- 顶部指标卡片和走势小图
- 右侧「命运追踪」栏和「一生之书」
- 编年史
- 明暗两套配色的设计变量写法

禾境的模拟是用规则跑的，不调用 AI。屿志也一样：除了以后的「问项目近况」，其余全部用规则计算。

## 3. 核心对照

| 禾境 | 屿志 |
|---|---|
| 居民 | 任务，住在所属项目的村落里 |
| 聚落 | 项目，一个项目是岛上的一个村落 |
| 五项指标 | 粮仓（今日精力和时间）、推进度、积压、状态 |
| 改变的种子 | 现实事件：突发截止日、生病、新项目进来 |
| 一生之书 | 一个项目从立项到完成或关闭的完整经历 |
| 编年史 | 每天结算后自动写下的一行记录 |
| 移民 | 新任务，乘船停在码头等你安排 |

## 4. 设计底线

这四条在任何功能取舍里都优先：

1. **输入不能比普通待办 App 多。** 小岛的变化全部由用户本来就在做的事驱动，维护小岛本身不能变成新负担。
2. **衰败要慢，恢复要快。** 落后再多，也要永远留着回来的路。
3. **最后一步由用户决定。** 项目不会自己消失，关闭、放弃、立为地标都要用户确认。
4. **主动放弃不是失败。** 标记「不重要了」是好的取舍，不惩罚，反而腾出空间。

## 5. 一天的循环

1. **早上，看一眼小岛。** 打开就是全景，不是任务列表。哪个村落热闹、哪个冷清、粮仓还剩多少、码头排了几条船，一眼看清。
2. **白天，处理码头。** 新任务停在码头。用户决定它住进哪个村落、排在什么时候，或者婉拒。安排时显示代价，例如「接下这件，某项目要推迟两天」。
3. **晚上，结算。** 逐条确认今天做了什么（见第 7 节），小岛据此变化，编年史自动多一行。

## 6. 数据来源

两类数据，扮演不同角色：

- **日历事件**：告诉小岛时间花在了哪里。决定村落热闹还是冷清。
- **用户自己创建的项目和任务**：告诉小岛你想建造什么。决定小岛往哪个方向长。

**日历导入：**

- MVP：用 .ics 订阅链接。Apple、Google、Outlook 都能导出这种链接，也支持上传 .ics 文件。只读。
- 以后：Google 和 Outlook 走官方授权接口，可以双向同步；Apple 走 CalDAV，放最后。

**事件归到哪个村落：**

日历事件本身不知道自己属于哪个项目。第一次遇到一类事件时让用户手动指定，系统记下一条规则（例如标题包含「周会」→ 团队）。之后同类事件自动归位，只有没匹配到规则的新事件才询问。没有归属的事件放在一个「杂务」区。

## 7. 晚间结算

**这是已定决定：过去的事件和任务不会默认算完成，需要用户确认。**

晚上打开时小岛进入黄昏，今天的事件和任务排成一列，每条只需一个动作：

- **右滑 = 做了**：变成一块砖，飞进所属村落
- **左滑 = 没做**：可选一个原因：被打断 / 没精力 / 不重要了 / 推到明天
- **轻点 = 做了一部分**

顶部有「全部做了」按钮，一次确认全部，再单独改例外。目标是大多数日子一分钟内结算完。

**忘了结算：**

- 第二天早上，昨天未结算的条目排在最上面
- 未结算的日子，小岛被海雾笼罩；补上记录雾就散
- 超过 3 天仍未结算，自动归档为「未记录」：不算做了，也不算没做，不产生任何后果

「没做」的原因会写进项目的一生之书，以后可以回答「这个项目为什么停滞」。

## 8. 后果：衰败与恢复

**这是已定决定：没做的事有可见的后果。**

村落按「距上次真实推进的天数」分阶段（以下天数是初始值，之后可调）：

| 阶段 | 天数 | 样子 |
|---|---|---|
| 正常 | 0–6 | 有人走动，晚上亮灯 |
| 安静 | 7–13 | 行人变少，亮灯的窗户变少 |
| 蒙灰 | 14–27 | 屋顶蒙灰，路边长杂草 |
| 搬离 | 28 起 | 居民开始离开，任务被标为「可能放弃」；弹出询问：重新启动 / 缩小规模 / 正式关闭 |

**不同原因，后果不同：**

- **推到明天**：单次无后果。同一任务连续推迟 3 次起，所属村落额外加重一档。
- **被打断**：后果很轻，但在码头留下一条「打断记录」，日后可以看出打断的来源。
- **没精力**：不伤害村落，而是降低粮仓。它提示的是整体太累。
- **不重要了**：任务移出，不算惩罚。

**恢复：**

每有一天真实推进，村落回退一个阶段。荒了一个月的村落，认真两三天就能恢复热闹。

## 9. 完成：落成仪式（第二版）

**这是已定决定：每个项目完成时，由用户选择去处。**

- 完成那一刻小岛暂停，显示这个项目一生之书的小结：立项日期、用时、推迟次数、主要卡点、关键转折。
- 用户选择：
  - **立为地标**：村落合成一座永久建筑，沿海岸建起
  - **收进档案馆**：村落腾空，项目放进山顶的灯塔（档案馆），可按年份翻看
- 选择可以反悔：地标可收进档案馆，档案里的项目可重新立起。
- 用户正式关闭的未完成项目，也进档案馆，放在另一个书架「未竟之书」，记录它为什么停下。

## 10. 小岛的视觉

**这是已定决定：沿用禾境的等距小岛风格。**

- **中心**是正在推进的村落
- **海岸**一圈圈是地标；地标越多，岛向外长出新陆地，像年轮
- **码头**停着待安排的任务船，积压越多船越多
- **山顶灯塔**是档案馆
- **海雾**表示未结算的日子
- **粮仓**表示今天的精力和时间
- **季节**跟随现实日期

## 11. 界面

屏幕上只有三样东西：

1. **小岛地图**：项目是村落，任务是住在里面的人
2. **顶部指标**：粮仓、推进度、积压、状态
3. **右侧追踪栏**：点开任何项目或任务，看它的一生之书

手机上：地图在上，指标压成两列，追踪栏变成从底部拉起的面板。晚间结算在手机上是主要场景，滑动手势要优先做好。

## 12. MVP 范围

**做：**

- 小岛地图（复用禾境），村落 = 项目
- 手动创建项目和任务
- .ics 链接导入和文件上传，事件归类规则
- 晚间结算（滑动确认、原因、全部做了、海雾、3 天归档）
- 衰败与恢复
- 顶部四项指标
- 一生之书（记录事件和原因，先做列表，不做小结页）
- 编年史
- 数据存在本地 IndexedDB，支持导出 / 导入 JSON 备份

**先不做：**

- 落成仪式、地标、档案馆
- 码头安排时的代价提示
- AI「问项目近况」
- Google / Outlook 授权同步、Apple CalDAV
- 账号和多设备同步

## 13. 指标的初始定义（可调）

- **粮仓**：今天的可用时间 = 设定的工作时段 − 日历上已排的时间。近 7 天里「没精力」每出现一次，建议容量下调一些。
- **推进度**：近 7 天确认「做了」的条目数，走势图显示每日数量。
- **积压**：码头上未安排的任务数 + 已过期未完成的任务数。
- **状态**：近 7 天已结算条目中「做了」和「做了一部分」的占比。

## 14. 数据模型草稿

```ts
interface Project {
  id: string;
  name: string;
  createdAt: string;          // ISO 日期
  lastProgressAt?: string;    // 最近一次确认「做了」的日期，用于计算衰败阶段
  status: 'active' | 'closed' | 'done';
  islandSlot: number;         // 在岛上的位置
}

interface Task {
  id: string;
  projectId?: string;         // 没有则停在码头
  title: string;
  scheduledFor?: string;      // 日期
  postponeCount: number;
  status: 'open' | 'done' | 'dropped';
}

interface CalendarSource {
  id: string;
  name: string;
  icsUrl?: string;            // 订阅链接
  lastFetchedAt?: string;
}

interface CalendarEvent {
  id: string;                 // 来源 id + 事件 UID + 开始时间，保证重复事件每次唯一
  sourceId: string;
  title: string;
  start: string;
  end: string;
  projectId?: string;         // 由归类规则或用户指定
}

interface ClassifyRule {
  id: string;
  contains: string;           // 标题包含的文字
  projectId: string;
}

type Outcome = 'done' | 'partial' | 'skipped';
type SkipReason = 'interrupted' | 'no_energy' | 'not_important' | 'postponed';

interface SettlementEntry {
  date: string;
  itemType: 'task' | 'event';
  itemId: string;
  outcome: Outcome;
  reason?: SkipReason;
}

interface ChronicleLine {
  date: string;
  text: string;               // 由规则生成，例如「今天推进了 3 件事，团队村落恢复了热闹」
}
```

## 15. 技术建议

- **技术栈**：TypeScript + Vite + Canvas，部署到 Cloudflare Pages（和流动日历一致，方便复用经验）
- **本地存储**：IndexedDB（可用 `idb` 这类小库）
- **.ics 读取**：浏览器不能直接跨站读取别人的 .ics 链接（跨域限制），需要一个 Cloudflare Worker 代为获取后返回。Worker 只做转发，不保存任何数据
- **.ics 解析**：用 `ical.js`，要正确处理重复事件（RRULE）和时区
- **结算判定**：每天的日期边界按用户本地时区计算

## 16. 建议的开发顺序

1. 搭项目骨架，把禾境的地图、配色变量、指标卡片搬进来，换成小岛上的村落
2. 数据层：IndexedDB 存取、导出 / 导入备份
3. 手动创建项目和任务，任务出现在对应村落
4. 晚间结算界面和滑动手势
5. 衰败阶段的计算和画面变化，恢复逻辑
6. 指标和编年史
7. Cloudflare Worker + .ics 导入 + 归类规则
8. 海雾和 3 天归档
9. 手机端打磨

每一步做完都能运行和看见效果，再进行下一步。
