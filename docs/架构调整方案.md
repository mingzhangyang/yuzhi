# 屿志 · 架构调整方案

> 2026-10-04 修订。代码核对基线：PR #6 的 `1d1ad84`。核心路线保留：纯规则、事实与派生分离、原子事务、单写者。本文同时记录设计契约、已实现机制与待验收工作；不能将“基础机制已实现”解释为所有 Phase 已完成。阶段状态及后续顺序见第 10 节。

## 1. 现状：做得对、要保留的

- **规则层是纯函数**：`src/logic/` 不碰 DOM，测试也集中在这一层。衰败由结算记录逐日重放得出（`logic/decay.ts`），不额外存状态，是整个项目最稳的部分。
- **全部数据放内存，写穿到 IndexedDB**（`store.ts`）：个人数据量很小，启动时全部载入、读时直接算，够用。
- **「今天」可替换**（`store.clock`），日期一律按本地时区的 `YYYY-MM-DD`。
- **.ics 代理只有一份**（`shared/icsProxy.ts`），Worker、Pages Function、Vite 开发服务器共用。
- **可调数值集中**在 `logic/config.ts`。
- **备份已有严格校验**，规则层、结算、衰败和导入导出也已有一批 Vitest 回归测试，可以作为迁移的安全网。

现阶段**不建议**：换 UI 框架、上后端、引入 CRDT 或多设备同步方案。先把本地单用户模型做干净，再决定是否扩大系统边界。

## 2. 目标数据模型：事实、操作、派生、冻结历史分开

这是本轮调整最重要的原则。

重构前，一次结算除了写 `entries`，还会顺手修改：

- 一生之书里的「做了 / 没做 / 阶段变化」
- `interruptions`
- `Project.lastProgressAt`
- `Project.lastStage`
- `Task.postponeCount`
- 任务的 `status / scheduledFor / closedAt`

旧实现改判时必须再通过 `revertEntry` 手动撤销这些后果。前几轮审查出现的「改判留下旧后果」「阶段变化重复」本质上都来自同一个问题：**同一事实被复制成了多份可写状态**。

但“只删掉几个缓存字段”还不够。任务状态和日期也不能继续依赖“旧结算反向修改现在的 Task”，否则会出现：

> 10 月 1 日结算为「推到明天」→ 之后用户手动把任务改到 10 月 5 日 → 再回头改判 10 月 1 日 → 回滚逻辑把 10 月 5 日覆盖掉。

当前设计将数据分成五类；不同类别具有不同的保全与重算规则。

| 类别 | 内容 | 处理 |
|---|---|---|
| **实体事实（存）** | 项目、任务、日历源、日历事件、归类规则里用户明确设定的内容 | 保持存储 |
| **行为事实（存）** | 结算 `entries`、每天结算状态 `days`、用户主动操作（立项、改期、搬村、关闭、重启、缩小规模、放下、落成、恢复地标等） | 作为事实保存，不靠“反向回滚”恢复 |
| **历史快照（存）** | 积压快照 `snapshots` | 本身就是历史采样，无法事后可靠推出 |
| **冻结叙述（存）** | 编年史 `chronicle` | 当时生成的话保持不变 |
| **派生视图（算）** | 结算产生的一生之书条目、打断记录、最近推进日、推迟次数、项目阶段与阶段转折 | 从事实重放 / 聚合得到 |

### 2.1 增加操作事实层

已引入轻量的 `OperationEvent`，保存用户主动操作，以及迁移所需的历史快照和状态基线。完整类型以 `src/types.ts` 为准。

示意：

```ts
interface OperationEvent {
  id: string;
  seq: number;       // 与 SettlementEntry 共用的持久化事实序号
  date: ISODate;      // 游戏规则仍按本地日期计算
  kind:
    | 'project-created'
    | 'project-renamed'
    | 'project-restarted'
    | 'project-trimmed'
    | 'project-closed'
    | 'project-completed'
    | 'project-resting-changed'
    | 'task-created'
    | 'task-arranged'
    | 'task-rescheduled'
    | 'task-moved'
    | 'task-dropped'
    | 'task-state-baseline'
    | 'migration-boundary'
    | 'legacy-life';
  projectId?: string;
  taskId?: string;
  payload?: Record<string, unknown>;
}
```

不要求把所有 UI 状态事件化，也不做通用 event-sourcing 框架。操作事实记录会影响后续计算的用户主动操作；迁移事实额外保全无法重建的叙述与状态基线。两者均有明确语义，不扩展为任意 UI 事件日志。

排序采用已实现的共享 `seq`：仅有 `YYYY-MM-DD` 无法判断同一天里“先推迟、后重启”还是“先重启、后推迟”。新事实的最终序号在 IndexedDB 事务内分配，内存中的临时序号在提交后校正；改判已有事实、改写事实 key 保留原序号。迁移追加序号必须从 `entries` 与 `operations` 的共同最大值继续。集合数组顺序、随机 id 和标签页时间戳不承担因果排序。

“一个事实只有一个权威来源”按字段语义解释：项目、任务等实体仍保存自身字段，`entries` / `operations` 负责结算与操作事实，`snapshots` / `chronicle` 保有独立历史语义。不能把这些集合误写成“只有 entries / operations 才是数据来源”。有效任务状态通过 read model 读取；原始实体记录仅用于其拥有字段的编辑。

### 2.2 结算只写结算事实

`SettlementEntry` 是某一天对某个任务 / 事件的判断。改判时：

- 修改或删除对应的 `SettlementEntry`
- 不再通过 `revertEntry` 逐项撤销 `life / interruption / lastStage / postponeCount`
- 当前任务状态、当前排期、推迟次数等由实体事实 + 操作事实 + 结算事实按顺序得到

当前已移除 `revertEntry`。后续变更继续遵守：改判修改事实，派生后果通过同一套重放规则重算。

### 2.3 明确派生项

以下内容已由 read model 计算，或从持久化模型中移除：

- 结算产生的一生之书行
- `interruptions`
- `Project.lastProgressAt`
- `Task.postponeCount`
- `Project.lastStage`
- 阶段变化史
- `LifeEntry.fromStage`

`computeVillage` 已经证明“从事实逐日重放”在这个项目的数据量下足够简单可靠。阶段历史也应沿用同一个计算源，避免小岛画面和一生之书各算一套。

### 2.4 历史保全依据来源事实，而不是仅看类型

旧 `life` 已退出当前业务模型，但旧数据库和旧备份仍须遵守以下迁移规则：

| 旧记录 | 迁移策略 |
|---|---|
| 有对应结算事实的结算叙述 | 使用结算 read model，不保留第二份可写副本 |
| 无对应结算事实的 `done` / `partial` / `skip` | 保留为带叙述快照的 `legacy-life` 操作，保全原文本和合法原因；不得伪造结算事实 |
| 主动操作历史 | 提升为操作事实，并保留当时叙述快照 |
| 已由 `legacyLifeId` 对应操作保全的记录 | 使用现有操作，避免重复迁移；对应操作必须包含有效快照 |
| `stage` | 按既定产品语义由当前规则重放；当时被冻结的编年史仍保留，见 2.5 |

v2 的主动操作选择与 v4 的历史保全是两种策略，不能共用主动类型白名单来决定删除哪些历史。当前 v4 保全映射穷举 `Exclude<LifeKind, 'stage'>`；新增类型时必须明确迁移处理方式。

一生之书是合并结算事实、操作叙述快照与阶段重放结果的 read model。删除旧集合的前提是完成这些语义转换并通过校验、持久化；转换失败不得提前销毁输入。

### 2.5 编年史与阶段规则的语义

阶段历史改成动态计算后，如果以后调整 `logic/config.ts` 的阶段阈值，过去的阶段转折可能变化。

这里明确采用：

- **小岛状态 / 一生之书里的阶段变化：按当前规则重新计算**
- **编年史：冻结为当时写下的叙述，不追溯改写**

因此未来可能出现“按今天规则看，当时应该晚两天进入蒙灰，但编年史仍保留当时规则下写出的那句话”。这是有意接受的语义：编年史记录的是“当时系统如何讲述这一天”，不是当前规则下的重新审判。

如果将来需要完全可复现的历史规则，再为 `chronicle` 增加规则版本；本轮不提前做。

## 3. 数据版本与迁移机制

纯迁移 runner 已建立。旧数据兼容、事务写回与连接生命周期必须一起定义。

### 3.1 区分三个概念

当前分开维护结构版本和业务版本：

- **`IDB_SCHEMA_VERSION`**：IndexedDB object store / index 的结构版本，用于结构升级及兼容性检查
- **`DATA_VERSION`**：屿志业务数据语义版本，保存在 `meta` 中
- **备份 `version`**：表示导出的业务数据版本，应与 `DATA_VERSION` 对齐

IndexedDB 新建 / 删除 object store 只能在 `upgrade()` 中处理；业务记录字段转换走数据迁移。两者可以在一次发布中同时发生，但不要用同一个数字假装它们是一回事。

### 3.2 统一纯数据迁移管线

维护有序迁移：

```ts
const migrations = [
  { to: 2, run(data) { /* ... */ } },
  { to: 3, run(data) { /* ... */ } },
];
```

要求：

- 每步只接受前一业务版本，输出下一版本
- 迁移尽量写成纯函数，便于 fixture 测试
- 迁移成功后才更新 `meta.dataVersion`
- 失败时旧数据保持可再次尝试迁移的状态
- 已迁移数据再次打开不得重复产生副作用

### 3.3 IndexedDB 分阶段升级与失败状态

当前版本为业务数据 v4、过渡 schema 7、最终 schema 8。版本号是本轮实现值，以下执行次序才是后续升级必须保持的契约。

写者在持有 lease 时执行：

1. 打开并检查现有 schema；拒绝未来 schema，以及当前/过渡 schema 缺少必要集合的情况。
2. 对需要升级的旧 schema，先进入**保留旧集合**的过渡结构；此时不得删除迁移输入。
3. 在一个只读事务中读取当前集合、旧集合、settings 和 `meta.dataVersion`，形成一致快照。
4. 在内存中逐版迁移并校验当前结构及关联关系。
5. 用一个读写事务提交全部业务集合、settings、新 `dataVersion` 和事实序号元数据。
6. 业务提交成功后才进入最终结构升级，删除旧集合。已在最终结构且无迁移需求时不重复升级。
7. 启动/接管只接受生命周期未变化的结果，再交给 Store；发生状态切换的旧结果必须丢弃或重新加载。

只读标签页不升级结构、不写迁移结果；可以在内存运行同一迁移得到只读视图。全新 profile 的无集合只读数据库作为未初始化数据处理；已有当前结构缺集合不能伪装为空数据。

| 失败位置 | 必须保留的状态与处理 |
|---|---|
| 不兼容版本、业务迁移或校验失败 | 保留已有记录，停止启动并显示错误，不以空白内存数据掩盖问题 |
| 迁移写回事务失败 | abort 并等待事务结束；旧数据和旧业务版本仍可重试，旧集合保留 |
| 业务提交成功、最终结构升级失败 | 已提交业务数据有效；下次根据实际 schema 与 dataVersion 继续清理，不重复生成事实 |
| 已识别的存储不可用错误 | 关闭候选连接后才允许临时内存降级；已有已校验恢复快照时必须携带该快照 |

未来 schema、结构缺损和业务版本损坏不属于可静默降级的存储不可用错误。

### 3.4 启动资源所有权

`initializePersistence` 在启动期间拥有候选持久层。成功后将持久层和数据交给应用；失败时先关闭候选连接，再传播原错误或选择内存持久层。调用方不得先丢弃引用、再指望 versionchange 回调或垃圾回收关闭数据库。

内存降级只提供临时会话，必须提示记录不会保存；数据校验错误不得转成新建空岛。正在运行的持久会话发生写入失败，仍按第 4 节回滚，不能自动换空白持久层。

### 3.5 旧备份导入

`parseBackup()` 与本地加载共用业务迁移管线，避免旧字段在迁移前被当前 `SHAPES` 拒绝。导入顺序：

1. 校验外壳：JSON、`format`、版本号类型
2. 按**该旧版本**能理解的最低要求读取原始数据
3. 运行同一套业务 migration
4. 对迁移后的当前版本执行严格 `SHAPES` + relation 校验
5. 用户确认后用原子 `replaceAll` 替换

导出只生成当前 `DATA_VERSION`。

### 3.6 日历事件 id 的特殊迁移

事件 id 的旧格式 → 新格式仍保留在 `mergeEvents` 附近处理，因为新 id 需要日历原始数据中的 RECURRENCE-ID / 原始开始时间，本地旧记录本身无法推出。

引用改写影响实体及结算/操作事实；不得再次引入 `life` 和 `interruptions` 的可写副本。事实改 key 仍保留持久化序号。

## 4. 原子写入：内存与 IndexedDB 必须一起原子

重构前，多次独立写入可能留下半套业务结果。当前 `Store.batch(fn)` 将同步动作合为一个持久事务，并维护已提交快照与待提交队列。

这里的原子性指持久事务全部提交或回滚，以及失败后的内存恢复。`batch()` 同步返回不代表已经落盘；内存可以暂时领先于磁盘，持久完成需要观察提交结果或 `flush()`。

### 4.1 batch 必须保证

一次 batch：

1. 所有持久化写入使用同一个 IndexedDB `readwrite` transaction
2. 内存修改有事务前快照或可回滚 change-set
3. 事务失败时：
   - 持久层确保事务 abort/回滚并等待结束
   - `store.data` 恢复到最近已提交快照，不能覆盖此前已成功提交的批次
   - UI 不得看到一个永久存在但磁盘没有的成功状态
4. 每个成功的持久事务触发一次 `onCommitted`；UI subscriber 通知按队列收敛合并，失败也应通知回滚状态
5. batch 内允许读取本批次内存修改；回调必须同步，嵌套 batch 共用外层事务

同步契约在入口强制执行：TypeScript 拒绝 PromiseLike 返回值，原生 async 回调（包括 bind 后的回调）在调用前拒绝。对普通函数包装异步返回值的动态调用，回滚同步前缀，并隔离写入直到返回的 thenable 结束，同时消费其拒绝，防止 await 后的 store.put 另起批次。所有异步契约违规统一记录到事务级错误状态：无论原生 async 还是动态 thenable，嵌套错误即使被外层捕获，也必须使整个外层批次回滚；不能由调用栈是否抛出来决定事务是否有效。

隔离是无效调用的失败保护，不是异步 batch 支持；永不结束的无效回调会持续禁止写入，不能定时解除后允许旧代码继续写入。异步读取应在 batch 外完成，经会话版本校验后再进入同步 batch；回调内也不得启动未纳入返回值的后台副作用。

### 4.2 缓存与通知要分开

不能简单在 batch 期间禁用 `changed()`。

例如 `settleDay()` 会在写结算记录后再次调用 `store.villages()` 比较阶段。如果 batch 内不推进数据版本，`villageCache` 会错误复用结算前的结果。

实现区分两个概念：

- **data revision / cache invalidation**：每次内存变化都立即发生
- **subscriber notification**：batch 期间合并，待当前队列收敛后通知最终成功或回滚状态

这样事务内部的计算看得到最新数据，但界面不会被半完成状态反复刷新。

### 4.3 首批必须纳入 batch 的操作

至少包括：

- `settleDay`
- `mergeEvents`
- `trimProject`
- `restartProject`
- `closeProject`
- `completeProject`
- `seedDemo`
- 备份导入 / `replaceAll`

后续所有“一个用户动作会写多条事实”的 action 默认都应使用 batch。

### 4.4 队列、失败传播与全量替换

- 普通批次按入队顺序提交；队列内后续批次可能依赖前面尚未提交的内存结果。
- 某批次失败后，当前待提交队列中依赖它的后续批次一并失败，不把基于失败状态的计算继续写入。此前已成功提交的批次保留；队列收敛后允许新动作重新开始。
- `flush()` 观察调用时的队列尾所对应的完成结果；多个等待者必须看到同一个成功或失败，不能由第一个等待者“消费”错误。它不承诺等待调用之后新增的批次。
- 需要排空全部写入的生命周期操作，先同步撤销新动作权限，再等待 `flush()`，避免边等待边加入新写入。
- `replaceAll()` 先建立独占屏障，拒绝期间的新业务批次，排空旧队列，然后捕获和提交替换数据。旧批次的序号回填不得越过替换边界污染导入数据；失败时释放屏障并保留正确的已提交状态。
- `reload()` 只用于没有在途业务写入的快照切换；会话编排负责满足这一前置条件。将该条件固化为接口保护及回归测试属于后续收尾验收，不能依赖调用者长期记住隐含规则。

## 5. 多标签页与会话生命周期

### 5.1 权威来源与职责

同源、同一浏览器存储环境中的页面使用同一 Web Lock 协调写入。`SingleWriterCoordinator` 是写生命周期的权威来源；只有 `writer` 状态接收新动作，Store 与 UI 的只读状态是它的投影。

Web Lock 提供互斥；BroadcastChannel 仅发送状态/提交通知，读者收到提交后重新读取数据库。通知不是锁，也不是持久事实。无 Web Locks 时当前策略为保持只读并明确提示，不启用未经验证的租约模拟。

需要区分三件事：

1. **能否接收新动作**：由 coordinator 状态决定。
2. **能否完成并广播已接受的提交**：由实际 lease 持有期决定，不能仅检查 `isWritable`。
3. **何时释放连接、锁和 channel**：由正在执行的清理流程决定，不等同于 UI 已显示只读。

### 5.2 状态与转换契约

| 状态 | 接收新动作 | lease 与退出条件 |
|---|---|---|
| `reader` | 否 | 稳定态无 lease；收到提交通知时刷新只读快照 |
| `preparing` | 否 | 获得 lease 后加载新快照；准备成功且状态未失效才能成为 writer |
| `writer` | 是 | 持有 lease；新写入排队提交 |
| `releasing` | 否 | 若原来持锁，排空在途写入并广播最终提交后释放，进入 reader |
| `recovering` | 否 | versionchange 恢复期间若持锁则保留至清理结束；关闭旧连接、按兼容性规则恢复只读快照 |
| `closed` | 否 | 终止态立即禁止新动作；可能仍在排空写入，结束后释放 lease 并关闭 channel，不可再次接管 |

`closed` 表示不再接收新操作，不表示异步清理已经结束。普通 relinquish 保留 channel 供后续接管；最终 close 才关闭 channel。

接管必须按“取得锁 → 只读准备 → 刷新成功 → 发布 writer”执行，不能把取得锁时的布尔结果当成之后永久有效的权限。启动使用稳定状态屏障；如果加载期间发生恢复/释放，丢弃旧生命周期的结果。

异步任务必须验证发起时的生命周期版本，不能只比较结束时的状态名称。`writer → reader → writer` 和 `reader → recovering → reader` 都产生新版本，旧请求不因此恢复有效。读者刷新通过 `runIfCurrent` 仅应用相同 coordinator revision 的结果；旧版本的读取错误也不得干扰恢复后的会话，当前版本的错误正常上报。

Store 的 `captureWriteContext(signal?)` 捕获 coordinator revision、只读权限变更代次与数据快照身份，并可绑定发起者的 AbortSignal；它们仅用于判定任务是否过期，不授予写权限。上下文从用户意图开始时捕获，而不是等文件选择或确认完成后重新取得。日历订阅、URL 添加、文件读取在异步等待后校验该上下文，错误回写也受同一上下文保护。整轮 autoRefresh 使用发起时的上下文，失效后不能在重新接管时继续下一订阅；reload、全量导入及内存回滚也会使旧快照任务失效。replaceAll 在排空写队列后也必须验证最初上下文，不能仅检查当下是否可写。

共享弹窗拥有独立的取消生命周期：每次关闭、替换或系统撤销都终止其 AbortSignal；取消生命周期与用户主动关闭回调分开，系统撤销不能触发 snooze 等业务写入。确认框在任意退出路径都会完成 Promise，旧按钮不能确认或关闭新弹窗。非 writer 状态统一撤销共享弹窗、结算与仪式界面。日历弹窗把取消信号传到异步服务，UI 续体也检查原上下文，防止旧请求更新复用的弹窗 DOM、提示或发起后续动作。备份导入和项目关闭确认跨 await 保留原上下文，即使确认已经返回 true，失权后重新取得 writer 也不能复活旧意图。取消丢弃未提交结果，不回滚关闭前已经提交的操作，也不等同于底层网络传输已被终止。

版本变化、bfcache 暂停和最终关闭都要先撤销新写入，再排空、通知、清理和释放。关闭与既有 drain 重叠时等待正在运行的 drain，不提前释放它的锁或 channel。后台日历刷新只由 writer 发起；失去权限后异步结果不得提交，恢复写者职责后再按需刷新。

### 5.3 会话编排收敛（待实施）

目前跨模块流程仍分布在 `main.ts` 的启动、接管、读者刷新、versionchange、pagehide/pageshow 和后台任务回调里。后续建立一个应用会话模块，统一编排这些流程；名称可为 `app-session.ts`，当前尚未创建。

| 模块 | 拥有的职责 | 不应承担的职责 |
|---|---|---|
| Coordinator | 锁、状态转换、状态/提交通知与稳定状态屏障 | 数据校验、业务迁移、DOM |
| Persistence | 数据库连接、结构兼容、事务、序号分配 | UI 权限和业务动作选择 |
| Store | 同步动作批次、队列、内存回滚、read model 缓存 | 浏览器生命周期和锁获取 |
| 应用会话 | 组织启动/接管/恢复/释放顺序、读者刷新、后台任务生命周期 | 复制业务规则，另建可写权限真相 |
| UI / `main.ts` | 组装依赖、订阅状态、渲染和传递用户意图 | 自行重连数据库或绕过会话恢复写权限 |

`initializePersistence` 已负责启动候选连接的所有权交接，可作为会话内部组件。持久层的访问模式是底层保护，不是独立于 coordinator 的用户写权限。

收敛时必须覆盖终止、恢复与准备的交叠；过期读者刷新不能覆盖新写者快照。终止过程排空写入是协作式清理，不能将页面退出等同于提交成功；持久成功仍以事务完成为准。可见页恢复时核对最新数据、补偿可能遗漏的通知，是后续会话与浏览器验收要求，不能仅凭发送过广播认定读者永久同步。

## 8. 测试门槛

“现有测试继续通过”只是最低要求。本轮架构调整必须新增以下回归测试。

### 8.1 migration fixtures

在 `tests/fixtures/` 保存至少一份真实旧版本形状的数据：

- 空数据
- 普通项目 + 任务
- 已结算 / 改判过的数据
- restart / trim / close / complete 历史
- 带旧 `life / interruptions / lastStage / postponeCount` 的数据
- v1 备份

验证：

- v1/v2/v3 分别迁至 current；备份导入和原地升级均保全所有合法非 stage 孤立历史
- 迁移幂等
- 迁移失败不会提前升级 `dataVersion` 或删除旧集合；配额故障发生在部分写入后仍完整回滚
- 旧备份导入后再导出，当前版本 round-trip 正常
- 已有来源事实与已迁移操作不重复生成；孤立叙述不改变结算状态
- 未来 schema、结构缺损及业务损坏拒绝加载；失败清理后后续结构升级不阻塞

### 8.2 原子事务测试

使用现有 `fake-indexeddb`：

- batch 中第 N 个写入故意失败
- IndexedDB 没有部分提交
- 内存恢复最近已提交状态，保留此前成功批次
- subscriber 不收到“成功完成”的最终状态
- 失败之后下一次正常写入仍可继续
- 较早批次成功、后续批次失败时保留正确提交边界，依赖失败状态的排队批次不继续写入
- 同一 flush generation 的多个等待者都得到相同失败，后续成功 generation 可以正常 flush
- replaceAll 与延迟事实写入并发时屏障生效，导入后的内存与磁盘序号一致
- async 回调执行前拒绝；包装 thenable 的回滚、延迟续写隔离、嵌套错误捕获和结束后恢复写入

### 8.3 改判与后续主动操作

至少覆盖：

- 推迟 → 用户手动改期 → 回头改判旧结算，手动改期不被覆盖
- 推迟 → 同日 restart → 推迟次数以事件顺序正确计算
- 改判 interrupted 后，派生的打断记录立即消失
- 改判推进结果后，最近推进日与阶段历史同步变化
- 删除 / 改写日历 event id 后，结算事实仍能正确指向新事件

### 8.4 多标签页与故障交叠

当前 `tests/single-writer.test.ts` 使用 FakeLocks / FakeChannel 与 fake-indexeddb，覆盖互斥、准备失败、稳定状态屏障、接管、只读限制、延迟提交及退出重叠。它们不能替代真实浏览器生命周期验收。

最新回归还覆盖权限往返期间的订阅成功/网络失败、URL/文件添加、整轮自动刷新中止、coordinator revision 与 reload/replaceAll 失效，以及 reader 恢复后的旧读取成功/失败。全部通过不能替代以下真实浏览器验证。

真实浏览器 smoke test **尚未在仓库建立，仍待完成**。最小范围：

- 同一 browser context 下 A、B 两页共享真实 IndexedDB / Web Locks / BroadcastChannel，始终只有一页可写。
