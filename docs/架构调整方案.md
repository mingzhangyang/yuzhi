# 屿志 · 架构调整方案

> 写于 MVP 完成、继续开发新功能之前。结论：现有架构对 MVP（个人使用、数据只存本地）是合适的，不需要推倒重来；但有两处结构性问题建议先处理——前两轮代码审查发现的问题，大半都出在这两处。

## 1. 现状：做得对、要保留的

- **规则层是纯函数**：`src/logic/` 不碰 DOM，测试也集中在这一层。衰败由结算记录逐日重放得出（`logic/decay.ts`），不额外存状态，是整个项目最稳的部分。
- **全部数据放内存，写穿到 IndexedDB**（`store.ts`）：个人数据量很小，读取简单，够用。
- **「今天」可替换**（`store.clock`），日期一律按本地时区的 `YYYY-MM-DD`。
- **.ics 代理只有一份**（`shared/icsProxy.ts`），Worker、Pages Function、Vite 开发服务器共用。
- **可调数值集中**在 `logic/config.ts`。

现阶段**不建议**：换 UI 框架、上后端、引入 CRDT 或同步方案——规模用不上。

## 2. 需要调整的地方（按优先级）

### 2.1 把「事实」和「派生数据」分开（最重要）

**问题**：一次结算除了写结算记录，还会顺手写一堆派生数据——一生之书里的「做了 / 没做 / 阶段变化」、打断记录、项目的 `lastProgressAt` 和 `lastStage`、任务的 `postponeCount`。改判时每一类都要手动撤销（`actions.ts` 里的 `revertEntry`、`LifeEntry.fromStage`、`renameEvent` 里的引用改写）。审查里「改判留下旧后果」「阶段变化重复」都源于此；以后每多一种派生数据，就多一处要记得撤销。

**方案**：只存事实，派生数据读的时候算。

| 类别 | 内容 | 处理 |
|---|---|---|
| 事实（存） | 项目、任务里用户设定的内容；结算记录 `entries`；每天的结算状态 `days`；用户的主动操作（立项、关闭、重启、缩小规模、落成、放下） | 保持存储 |
| 事实（存） | 积压快照 `snapshots` | 它本身就是历史，无法事后推出，保持存储 |
| 派生（改为计算） | 一生之书里由结算产生的条目 | 由 `entries` 生成 |
| 派生（改为计算） | 打断记录 `interruptions` | 就是原因为「被打断」的结算记录 |
| 派生（改为计算） | `Project.lastProgressAt` | 由 `entries` 算 |
| 派生（改为计算） | `Task.postponeCount` | 最近一次重置之后「推迟」记录的条数（重置作为一条操作记录保存） |
| 派生（改为计算） | 阶段变化史、`Project.lastStage` | 沿用 `computeVillage` 的逐日重放，顺便记下每天的阶段，转折点自然得出；一生之书与小岛画面永远一致 |
| 叙述（存，冻结） | 编年史 `chronicle` | 当时写下的话，保持固定 id 存储 |

**完成后**：改判只是改结算记录本身；`revertEntry` 只剩任务的状态和日期；`lastStage`、`fromStage`、`interruptions` 集合可以删掉。

**待决定**：阶段史改为计算后，若日后调整 `config.ts` 的阈值，过去的阶段史会跟着变。建议接受（村落状态本来就是这样算的）；若希望历史冻结，则阶段史继续存储。

### 2.2 原子写入与多标签页

**问题**：
- 每次 `store.put` 是一个独立的 IndexedDB 事务，一次结算可能几十个；写到一半关掉页面，会留下半套数据。
- 两个标签页各有一份内存数据，会互相覆盖；也没处理 `versionchange`，以后升级数据库版本时，另一个开着的标签页会把升级卡住。

**方案**：
- `Store.batch(fn)`：把一次操作的所有写入合进一个事务。`settleDay`、`mergeEvents`、`trimProject`、`seedDemo` 等多步操作都包进去（示例数据的失败回滚也就不必再靠整份快照）。
- 多标签页：用 `BroadcastChannel` 通知其他标签页重新载入；或更简单——只允许一个标签页写入，其他标签页提示「已在另一个标签页打开」。同时处理 `versionchange`（关闭连接并提示刷新）。

### 2.3 数据迁移机制

**问题**：升级数据库版本目前只会新建存储区；备份格式固定为 v1；这次事件 id 的迁移是临时写在 `mergeEvents` 里的。

**方案**：在 `meta` 里记数据版本号，维护一个有序迁移列表 `[{ to, run(data) }]`。打开数据库和导入旧备份走同一条迁移管线。2.1 就是第一个要用上它的改动。

例外：日历事件 id 的迁移只能留在合并日历时做——新 id 需要日历里原本的开始时间（RECURRENCE-ID），本地数据里没有。

### 2.4 结构整理（低优先级，顺手做）

- `actions.ts`（约 525 行）按领域拆分：项目、任务、结算、日历、落成。
- `main.ts` 的 `update()` 是界面刷新函数，却会写积压快照（`recordBacklogSnapshot`），应移到数据变化之后去写。
- `ui/tracker.ts`（约 690 行）、`island/render.ts`（约 970 行）现在还能维护，下次改到时再拆。

## 3. 与后续功能的关系

| 功能（交接文档「先不做」） | 对架构的要求 |
|---|---|
| 码头安排时的代价提示 | 纯规则，现有结构直接支持 |
| AI「问项目近况」 | Worker 要加接口并把项目数据发出去，和「Worker 只转发、不保存」的定位不同，属于产品决定。2.1 完成后，喂给 AI 的上下文由事实生成，更干净 |
| Google / Outlook 双向同步 | 授权凭证必须存服务端，需要 KV/D1 与账号，是大决定 |
| 账号与多设备同步 | 2.1、2.2 是前提：只同步事实，派生数据各端自己算，冲突少很多；之后再给记录加 `updatedAt` 和删除标记 |

## 4. 建议顺序

1. 2.1 事实与派生分离，同时搭好 2.3 迁移机制（这次就要用）。
2. 2.2 批量写入与多标签页。
3. 2.4 穿插在后续功能里做。

前三步不改界面和用户可见行为，现有单元测试作为回归保障。
