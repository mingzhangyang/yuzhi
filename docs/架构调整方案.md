# 屿志 · 架构调整方案

> 写于 MVP 完成、继续开发新功能之前。结论：现有架构对 MVP（个人使用、数据只存本地）是合适的，不需要推倒重来。接下来的重点不是换框架，而是把数据语义、迁移和事务边界先收紧，避免继续增加功能后让“改判 / 回滚 / 迁移 / 多标签页”越来越难维护。

## 1. 现状：做得对、要保留的

- **规则层是纯函数**：`src/logic/` 不碰 DOM，测试也集中在这一层。衰败由结算记录逐日重放得出（`logic/decay.ts`），不额外存状态，是整个项目最稳的部分。
- **全部数据放内存，写穿到 IndexedDB**（`store.ts`）：个人数据量很小，启动时全部载入、读时直接算，够用。
- **「今天」可替换**（`store.clock`），日期一律按本地时区的 `YYYY-MM-DD`。
- **.ics 代理只有一份**（`shared/icsProxy.ts`），Worker、Pages Function、Vite 开发服务器共用。
- **可调数值集中**在 `logic/config.ts`。
- **备份已有严格校验**，规则层、结算、衰败和导入导出也已有一批 Vitest 回归测试，可以作为迁移的安全网。

现阶段**不建议**：换 UI 框架、上后端、引入 CRDT 或多设备同步方案。先把本地单用户模型做干净，再决定是否扩大系统边界。

---

## 2. 目标数据模型：事实、操作、派生、冻结历史分开

这是本轮调整最重要的原则。

当前一次结算除了写 `entries`，还会顺手修改：

- 一生之书里的「做了 / 没做 / 阶段变化」
- `interruptions`
- `Project.lastProgressAt`
- `Project.lastStage`
- `Task.postponeCount`
- 任务的 `status / scheduledFor / closedAt`

改判时必须再通过 `revertEntry` 手动撤销这些后果。前几轮审查出现的「改判留下旧后果」「阶段变化重复」本质上都来自同一个问题：**同一事实被复制成了多份可写状态**。

但“只删掉几个缓存字段”还不够。任务状态和日期也不能继续依赖“旧结算反向修改现在的 Task”，否则会出现：

> 10 月 1 日结算为「推到明天」→ 之后用户手动把任务改到 10 月 5 日 → 再回头改判 10 月 1 日 → 回滚逻辑把 10 月 5 日覆盖掉。

因此需要把数据分成四类。

| 类别 | 内容 | 处理 |
|---|---|---|
| **实体事实（存）** | 项目、任务、日历源、日历事件、归类规则里用户明确设定的内容 | 保持存储 |
| **行为事实（存）** | 结算 `entries`、每天结算状态 `days`、用户主动操作（立项、改期、搬村、关闭、重启、缩小规模、放下、落成、恢复地标等） | 作为事实保存，不靠“反向回滚”恢复 |
| **历史快照（存）** | 积压快照 `snapshots` | 本身就是历史采样，无法事后可靠推出 |
| **冻结叙述（存）** | 编年史 `chronicle` | 当时生成的话保持不变 |
| **派生视图（算）** | 结算产生的一生之书条目、打断记录、最近推进日、推迟次数、项目阶段与阶段转折 | 从事实重放 / 聚合得到 |

### 2.1 增加操作事实层

建议增加轻量的 `OperationEvent`（最终名称可调整），用于保存“用户主动改变了什么”。

示意：

```ts
interface OperationEvent {
  id: string;
  occurredAt: string; // ISO 时间戳，用于同一天内排序
  date: ISODate;      // 游戏规则仍按本地日期计算
  kind:
    | 'project-created'
    | 'project-renamed'
    | 'project-restarted'
    | 'project-trimmed'
    | 'project-closed'
    | 'project-completed'
    | 'project-resting-changed'
    | 'task-created'
    | 'task-arranged'
    | 'task-rescheduled'
    | 'task-moved'
    | 'task-dropped';
  projectId?: string;
  taskId?: string;
  payload?: Record<string, unknown>;
}
```

不要求把所有 UI 状态事件化，也不做通用 event-sourcing 框架。这里只记录**会影响之后计算、且改判时不能被旧结算覆盖的用户主动操作**。

`occurredAt`（或单调递增 `seq`）是必要的：仅有 `YYYY-MM-DD` 无法判断同一天里“先推迟、后重启”还是“先重启、后推迟”。

### 2.2 结算只写结算事实

`SettlementEntry` 是某一天对某个任务 / 事件的判断。改判时：

- 修改或删除对应的 `SettlementEntry`
- 不再通过 `revertEntry` 逐项撤销 `life / interruption / lastStage / postponeCount`
- 当前任务状态、当前排期、推迟次数等由实体事实 + 操作事实 + 结算事实按顺序得到

完成后目标是**删除 `revertEntry` 这种“猜测旧状态”的逆操作逻辑**，而不是只把它缩小。

### 2.3 明确派生项

以下内容应改为计算：

- 结算产生的一生之书行
- `interruptions`
- `Project.lastProgressAt`
- `Task.postponeCount`
- `Project.lastStage`
- 阶段变化史
- `LifeEntry.fromStage`

`computeVillage` 已经证明“从事实逐日重放”在这个项目的数据量下足够简单可靠。阶段历史也应沿用同一个计算源，避免小岛画面和一生之书各算一套。

### 2.4 一生之书不能整表直接删除

现有 `life` 同时混有两类内容：

1. 可由结算 / 阶段重放推出的内容，例如 `done / partial / skip / stage`
2. 用户主动操作产生的历史，例如立项、改名、搬村、重启、缩小规模、关闭、落成等

第一类应改为派生；第二类必须迁入操作事实，不能在迁移时丢失。

最终一生之书应成为一个 **read model**：按时间把结算事实、操作事实和阶段重放结果合并展示，而不是自己继续作为业务真相来源。

### 2.5 编年史与阶段规则的语义

阶段历史改成动态计算后，如果以后调整 `logic/config.ts` 的阶段阈值，过去的阶段转折可能变化。

这里明确采用：

- **小岛状态 / 一生之书里的阶段变化：按当前规则重新计算**
- **编年史：冻结为当时写下的叙述，不追溯改写**

因此未来可能出现“按今天规则看，当时应该晚两天进入蒙灰，但编年史仍保留当时规则下写出的那句话”。这是有意接受的语义：编年史记录的是“当时系统如何讲述这一天”，不是当前规则下的重新审判。

如果将来需要完全可复现的历史规则，再为 `chronicle` 增加规则版本；本轮不提前做。

## 3. 数据版本与迁移机制

这是第一阶段就要先搭好的基础设施，不应等 2.1 写完再补。

### 3.1 区分三个概念

当前已有 `DB_VERSION` 和 `BACKUP_VERSION`，后续必须避免混用。

建议明确：

- **`IDB_SCHEMA_VERSION`**：IndexedDB object store / index 的结构版本，只用于 `openDB(..., version, { upgrade })`
- **`DATA_VERSION`**：屿志业务数据语义版本，保存在 `meta` 中
- **备份 `version`**：表示导出的业务数据版本，应与 `DATA_VERSION` 对齐

IndexedDB 新建 / 删除 object store 只能在 `upgrade()` 中处理；业务记录字段转换走数据迁移。两者可以在一次发布中同时发生，但不要用同一个数字假装它们是一回事。

### 3.2 统一纯数据迁移管线

维护有序迁移：

```ts
const migrations = [
  { to: 2, run(data) { /* ... */ } },
  { to: 3, run(data) { /* ... */ } },
];
```

要求：

- 每步只接受前一业务版本，输出下一版本
- 迁移尽量写成纯函数，便于 fixture 测试
- 迁移成功后才更新 `meta.dataVersion`
- 失败时旧数据保持可再次尝试迁移的状态
- 已迁移数据再次打开不得重复产生副作用

### 3.3 IndexedDB 打开流程

推荐顺序：

1. IndexedDB schema upgrade：只处理 store / index 结构
2. 读出全部原始业务数据和 `meta.dataVersion`
3. 在内存中按顺序跑业务迁移
4. 用一个事务写回迁移后的完整数据 + 新 `dataVersion`
5. 成功后才把结果交给 `Store`

这样不会出现“部分集合已经是新结构、另一半还是旧语义”的状态。

### 3.4 旧备份导入

当前 `parseBackup()` 会直接按当前 `SHAPES` 校验。架构调整后不能再这样做，否则旧备份可能在迁移前就因“字段和当前 schema 不一致”被拒绝。

导入顺序应改为：

1. 校验外壳：JSON、`format`、版本号类型
2. 按**该旧版本**能理解的最低要求读取原始数据
3. 运行同一套业务 migration
4. 对迁移后的当前版本执行严格 `SHAPES` + relation 校验
5. 用户确认后用原子 `replaceAll` 替换

导出只生成当前 `DATA_VERSION`。

### 3.5 日历事件 id 的特殊迁移

事件 id 的旧格式 → 新格式仍保留在 `mergeEvents` 附近处理，因为新 id 需要日历原始数据中的 RECURRENCE-ID / 原始开始时间，本地旧记录本身无法推出。

但迁移完成 2.1 后，引用改写只应影响真实事实；不应再需要同步修改一份 `life` 和 `interruptions` 派生副本。

## 4. 原子写入：内存与 IndexedDB 必须一起原子

当前每次 `store.put` 都立即改内存，再排队执行一个独立 IndexedDB 事务。一次结算可能几十次写入；页面中途关闭或写盘失败会留下半套数据。

需要 `Store.batch(fn)`，但它的契约必须比“把多次 put 放进一个 IDB transaction”更严格。

### 4.1 batch 必须保证

一次 batch：

1. 所有持久化写入使用同一个 IndexedDB `readwrite` transaction
2. 内存修改有事务前快照或可回滚 change-set
3. 事务失败时：
   - IndexedDB 自动回滚
   - `store.data` 同步恢复
   - UI 不得看到一个永久存在但磁盘没有的成功状态
4. 事务成功后再对外形成一次稳定通知
5. batch 内允许继续读取刚刚修改过的内存状态

### 4.2 缓存与通知要分开

不能简单在 batch 期间禁用 `changed()`。

例如 `settleDay()` 会在写结算记录后再次调用 `store.villages()` 比较阶段。如果 batch 内不推进数据版本，`villageCache` 会错误复用结算前的结果。

因此建议拆成两个概念：

- **data revision / cache invalidation**：每次内存变化都立即发生
- **subscriber notification**：batch 期间合并，commit 后只发一次

这样事务内部的计算看得到最新数据，但界面不会被半完成状态反复刷新。

### 4.3 首批必须纳入 batch 的操作

至少包括：

- `settleDay`
- `mergeEvents`
- `trimProject`
- `restartProject`
- `closeProject`
- `completeProject`
- `seedDemo`
- 备份导入 / `replaceAll`

后续所有“一个用户动作会写多条事实”的 action 默认都应使用 batch。

## 5. 多标签页：采用单写者，不把 BroadcastChannel 当并发控制

两个标签页各有一份完整内存数据。即使使用 `BroadcastChannel` 通知“请重新加载”，两个标签页仍可能同时从旧状态计算并提交，造成 lost update。

因此本轮明确采用 **single writer**：

- 同一浏览器 profile 下，同一时刻只允许一个屿志页面获得写权限
- 其他标签页进入只读状态，并明确提示「屿志已在另一个标签页打开」
- writer 释放后，只读页可以重新申请写权限
- `BroadcastChannel` 只负责：
  - writer 状态通知
  - commit 后提醒只读页刷新
  - 不负责互斥本身
- 同时处理 IndexedDB `versionchange`：关闭旧连接并提示刷新，不能让旧标签页阻塞数据库升级

实现 writer ownership 时优先使用浏览器提供的互斥能力；如果目标浏览器支持范围不足，再增加可靠的租约 / fallback。**不要用“谁最后广播谁赢”的方式模拟锁。**

## 6. 积压快照与 UI 副作用

`main.ts -> update()` 是渲染刷新函数，目前却会调用 `recordBacklogSnapshot(store)` 写数据。

这会导致：

- render 触发 write
- write 又触发 render
- 数据历史依赖“界面有没有刷新”
- batch / 多标签页后更难定义什么时候算一次真实业务变更

应把积压快照移动到会改变 backlog 的业务操作之后，或做成统一的 commit hook：

> 一次事实事务 commit → 重新计算今天 backlog → 若值变了，同事务或紧随其后的明确历史记录步骤写 snapshot。

目标是让 `update()` 变成纯读 / 纯渲染函数。

低优先级，但可随对应迁移顺手完成：

- `actions.ts` 按领域拆分：

## 8. 测试门槛

“现有测试继续通过”只是最低要求。本轮架构调整必须新增以下回归测试。

### 8.1 migration fixtures

在 `tests/fixtures/` 保存至少一份真实旧版本形状的数据：

- 空数据
- 普通项目 + 任务
- 已结算 / 改判过的数据
- restart / trim / close / complete 历史
- 带旧 `life / interruptions / lastStage / postponeCount` 的数据
- v1 备份

验证：

- `v1 -> current` 迁移结果正确
- 迁移幂等
- 迁移失败不会提前升级 `dataVersion`
- 旧备份导入后再导出，当前版本 round-trip 正常

### 8.2 原子事务测试

使用现有 `fake-indexeddb`：

- batch 中第 N 个写入故意失败
- IndexedDB 没有部分提交
- 内存恢复事务前状态
- subscriber 不收到“成功完成”的最终状态
- 失败之后下一次正常写入仍可继续

### 8.3 改判与后续主动操作

至少覆盖：

- 推迟 → 用户手动改期 → 回头改判旧结算，手动改期不被覆盖
- 推迟 → 同日 restart → 推迟次数以事件顺序正确计算
- 改判 interrupted 后，派生的打断记录立即消失
- 改判推进结果后，最近推进日与阶段历史同步变化
- 删除 / 改写日历 event id 后，结算事实仍能正确指向新事件

### 8.4 多标签页

对 writer ownership 的纯逻辑做单测，并至少保留一条浏览器级 smoke test：

- A 获得 writer
- B 只能读
- A 释放后 B 可接管
- `versionchange` 时旧连接关闭，不阻塞升级

| 功能 | 对架构的要求 |
|---|---|
| 码头安排时的代价提示 | 纯规则，事实 / 派生分离后更容易做“如果接下会怎样”的模拟 |
| AI「问项目近况」 | Worker 要加接口并把项目数据发出去，属于产品决定；架构调整后可从事实生成干净上下文 |

| 规则阈值调整 | 小岛 / 阶段 read model 可重算；冻结 chronicle 不追溯改写 |

## 10. 建议实施顺序

不要把 2.1、2.2、2.3 一次性塞进一个大 PR。按下面顺序推进，每一步都保持应用可运行。

### Phase 0 — Migration foundation

目标：先建立安全地修改数据模型的能力。

- 引入 `IDB_SCHEMA_VERSION` / `DATA_VERSION`
- `meta.dataVersion`
- 纯数据 migration runner
- 旧版本 fixture
- 打开数据库与导入备份共用迁移管线
- 补 `versionchange` 基础处理

**此阶段不改变用户可见行为和现有业务字段。**

### Phase 1 — Operation facts

目标：把用户主动操作从 `life` 的叙述副本提升为真实事实。

- 引入 `OperationEvent`
- 为需要排序的事实增加 `occurredAt` 或 `seq`
- 把 restart / trim / reschedule / move / close / complete 等主动操作写成事实
- 迁移旧 `life` 中无法重建的主动操作历史
- 一生之书开始从 operation + 旧兼容数据组合读取

### Phase 2 — Derived-state removal

目标：真正消除结算的反向回滚链。

- `interruptions` 改为派生
- `lastProgressAt` 改为派生
- `postponeCount` 改为派生
- `lastStage / fromStage` 删除
- 阶段历史按重放生成
- 结算产生的 `life` 行删除存储副本
- 改判只改 / 删事实，不恢复“猜出来的旧对象”

完成标准：`revertEntry` 不再承担业务回滚职责，最好直接删除。

### Phase 3 — Atomic batch

目标：一个用户动作 = 一个原子提交。

- Persistence transaction API
- `Store.batch(fn)`
- 内存 rollback
- cache revision 与 UI notification 分离
- 多步 action 全部迁入 batch
- snapshot 写入从 render 路径移出

### Phase 4 — Single-writer tabs

目标：解决多标签页 lost update 和数据库升级阻塞。

- writer ownership
- 只读页提示
- BroadcastChannel 状态通知 / reload
- versionchange 完整处理
- 接管与释放测试

### Phase 5 — Structural cleanup

- 按领域拆 `actions.ts`
- 清理迁移期兼容代码
- 删除废弃 collection / type / helper
- 更新 README 数据架构说明

## 11. 每个 Phase 的合并条件

每个架构 PR 合并前至少满足：

1. `npm run typecheck`
2. `npm test`
3. `npm run build`
4. 新增的 migration / transaction / replay 测试通过
5. 不改变未声明的用户可见行为
6. 不把下一 Phase 的工作提前混进当前 PR
7. 迁移旧数据前后有 fixture 对照，不能只测试“新建一份空数据库”

本轮架构调整的核心不是“代码更漂亮”，而是建立三个长期不变量：

> **一个事实只保存一次；一个用户动作要么全部成功、要么全部失败；旧数据永远有明确的升级路径。**

## 12. PR #6 生命周期边界约束

- **历史保全与主动操作选择分开。** v2 只提升主动操作；v4 删除旧 `life` 集合前，必须保全每一种非 `stage` 历史。没有对应结算事实的 `done` / `partial` / `skip` 保存为 `legacy-life` 叙述快照，不伪造结算事实，也不改变结算派生状态。保全映射穷举 `Exclude<LifeKind, 'stage'>`，新增类型时由类型检查要求补齐策略。
- **新写入权限与在途提交的完成分开。** `writer` 状态只决定能否接收新动作；实际 Web Lock 持有期决定能否广播已提交事实。`releasing` / `recovering` / `closed` 都先停止新动作，再排空写入并通知读者，最后释放 lease、关闭 channel。关闭与既有 drain 重叠时必须等待同一 drain。
- **启动资源所有权集中。** `initializePersistence` 持有候选持久层，加载成功才交给 Store；任意加载失败都先关闭连接，再传播数据错误或按已校验快照降级到内存。迁移写回事务失败必须先 abort 并等待事务结束，不能让部分写入在连接清理时提交。

验证覆盖 v1/v2/v3 备份与 IndexedDB 升级、历史去重和导出再导入、三种退出路径中的延迟提交与读者刷新、退出重叠，以及配额失败后的事务回滚和后续 schema 升级不阻塞。
