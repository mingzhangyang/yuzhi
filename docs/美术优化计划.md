## 1. 现状评估

以下结论来自 2026-11-02 的实机截图（夏 / 春 / 秋 / 冬白天、夏季黄昏与夜晚、放大到 2.8 倍的村落 / 码头 / 地标、三座村落同时处于「搬离」、手机 390px）以及绘制代码。

**做得好、要保留的：** 等距构图清晰；昼夜、季节、天气、积雪、节日、人物和树木的程序化系统完整；地块随机数按坐标哈希，岛的生长稳定；绘制与点击判定共用同一份几何；减弱动态效果（`calm`）已贯穿各处。

**与方向板的差距：** 方向板的关键词是「温润材质、手绘质感、有起伏的岛」。现在的小岛是干净的扁平矢量，整体偏平、偏空、偏冷，并且同时存在两种画风。

| # | 问题 | 现象 | 代码位置 |
|---|---|---|---|

**性能基线（2026-11-02，headless Chromium，8 座村落 + 3 座地标，单帧 `step + draw`）：**

| 视口 | CPU | 白天中位 / p95 | 夜晚中位 / p95 |
|---|---|---|---|
| 桌面 1280×860 @2x | 1× | 4 / 11 ms | 5 / 7 ms |
| 桌面 1280×860 @2x | 4× 降速 | 21 / 29 ms | 28 / 34 ms |
| 手机 390×844 @3x | 1× | 4 / 98 ms | 5 / 109 ms |
| 手机 390×844 @3x | 4× 降速 | 20 / 474 ms | 25 / 517 ms |

- 空闲帧率是 30 帧（每帧预算约 33 ms）。CPU 降速 4 倍时，夜晚的中位数已经接近预算，**加细节必须同时省出预算**。
- 手机模拟下大约每 11 帧出现一次 100 ms 以上的长帧，耗时分散在树、山、房子、人物的各个 `fill` 调用上，不是地面缓存失效。这更像 headless 软件光栅化的批量提交，**需要真机复核**（A4）后再下结论。（A4 headless 复核：帧间让出 rAF 后长帧基本消失，不让出则同一份代码能复现上表的 p95，见 9.1 节；真机复核仍待做。）
- 树、山、房子目前每帧都重画。地面已经有离屏缓存（`groundKey`），静态建筑层还没有。

## 2. 目标与非目标

**目标**
1. 对齐方向板：温润的配色、轻手绘质感、更丰富的地表与海。
2. 让画面承载信息：衰败阶段、培育等级、粮仓余量在**手机不放大**时一眼可读。
3. 统一画风：道具、建筑、地形看起来出自同一只手。
4. 不增加性能负担：空闲 30 帧、低端设备不掉帧。

**非目标**
- 不换渲染技术（仍是 Canvas 2D 程序化绘制），不引入 WebGL / 3D。
- 不改 `src/logic/` 里的任何规则，不改点击、键盘浏览和说明卡片的语义。
- 不新增玩法或操作；不加浇水、施肥之类的按钮（培育区仍然只是现实事实的 read model）。
- 不替换昼夜、天气、季节系统本身，只改它们的调色方式。

## 3. 原则（每一期都要遵守）

1. **方向板为准，程序化重绘优先。** 贴图用来增强视觉锚点，不替换 Canvas 绘制体系（沿用 `docs/art/README.md` 的使用原则）。
2. **画面语义服从三层模型。** 由数据驱动的新视觉（衰败细节、路面磨损、冬天扫出的路）只读**后果层**（`entries` / `operations` / `days` 的派生结果），不读此刻层；不能让「开过会」看起来像「盖了房」。
3. **一个元素只表达一个事实。** 新加的装饰不能和已有符号重名：炊烟已经表示天气和傍晚，小人等于任务，船等于码头上的任务。新增的带含义元素要在 `src/island/info.ts` 里能点开解释。
4. **全景可读是验收标准。** 手机 390px、不放大时，状态差异必须看得出来；只在放大后才看得到的细节只能算装饰。
5. **几何共享。** 绘制和点击 / 遮挡共用轮廓（`occluders`、`treeOutline`、`rectOutline`、`labelBox`）；改形状必须同步改轮廓，并跑 `browser-tests/agenda-hit-smoke.mjs`。
6. **静态进缓存，每帧只画会动的。** 新的地表细节画进地面离屏缓存（缓存键 `groundKey` 要包含所有影响它的输入）；每帧新增的绘制要有预算（见第 4 节）。
7. **颜色只从调色板派生。** 季节、昼夜、积雪、主题都通过同一组函数从调色板计算，不再写新的十六进制字面量。
8. **尊重减弱动态效果。** 新动画在 `calm` 下要么静止、要么直接到终态。
9. **每期可单独合并、可回退。** 前一期不依赖后一期的视觉效果。

### 4.1 截图矩阵

扩展现有的 `browser-tests/island-shots.mjs`（已经固定了随机数、id 和时钟，同一份代码两次运行得到同一张图），增加以下场景，作为每期的「改前 / 改后」对照：

| 组 | 场景 | 视口 |
|---|---|---|
| 时间 | 夏季 10:30、18:50（黄昏）、21:30（夜） | 桌面 @2x、手机 @3x |
| 季节 | 春 4 月、秋 10 月、冬 1 月（积雪）白天 | 桌面、手机 |
| 衰败 | 四座村落，最近一次推进分别在 0 / 8 / 15 / 29 天前（对应正常 / 安静 / 蒙灰 / 搬离） | 手机（不放大） |
| 培育 | 四个培育区分别取 0–4 级（通过构造结算、日记事实得到，不改规则） | 手机（不放大）+ 桌面 2.8 倍 |
| 近景 | 2.8 倍放大：一座村落、码头、一座地标 | 桌面 |
| 主题 | 暗色主题下的白天与夜晚 | 桌面 |

截图输出到被 git 忽略的 `shots/`，PR 描述里附关键对比图。

**已实现（A3）。** `island-shots.mjs` 按上表输出 `<组>-<场景>-<视口>.png`，另有：

- `-blind` 版：衰败与培育的手机截图再出一张不画标签的，直接用于 4.2 节盲看。
- 培育区的 2.8 倍近景每区一张（四个区域分散在岛上，2.8 倍下一屏装不下）。
- `cover` 组（不在上表里）：八种地标的昼 / 夜 / 雪、日程进行中、雨天、下雪，以及春节、端午、中秋、国庆、圣诞。用来保证调色板迁移这类「不该改观感」的改动在这些分支上也逐像素一致。
- 衰败场景用四座同样 15 块砖的村落，项目在最近一次推进的当天立起，确保阶段只由「几天没推进」决定；培育场景没有村落，四个区域同时处于同一等级（构造方法见脚本注释）。
- B 期新增两组：`cult-winter-l0…4`（与 `cult` 同样的数据放到冬 1 月积雪，手机含 `-blind`、桌面 2.8 倍每区一张）和 `granary-empty / half / full / busy`（桌面 2.8 倍）加 `granary-pano-empty`（手机全景）。粮仓的余量由时间账本算出，铺数据很难凑到指定比例，这一组在画面层直接给定 `granaryRatio` / `granaryBusy`，只改这一帧的画法输入，不碰规则。矩阵共 95 张。

对比用 `browser-tests/shot-diff.mjs <改前> <改后> [差异图目录]`：逐像素比较同名截图，报告差异像素数与最大通道差，可另存标红的差异图；全部一致时退出码为 0。截图前会把动画时钟、页面随机数、模拟层自己的随机源（雨丝、烟花、小人选目的地）和飘落物一起归位，同一份代码两次运行的 60 张截图逐像素一致。

### 4.4 测试

### 5.1 A 期：基础

- 从方向板取样的初始值如下（取色块中心 15×15 像素的中位数）。色块带水彩纹理，**需要人工校准后再定稿**：

  | 名称 | 取样值 | 用途 |
  |---|---|---|
  | 海水蓝 | `#92cbd0` | 浅水、河 |
  | 深海蓝 | `#356181` | 远海、夜晚的海 |
  | 春草绿 | `#92a55f` | 春季草地基色 |
  | 夏日绿 | `#567d68` | 夏季林地、深色草 |
  | 秋麦黄 | `#ebb664` | 农田、秋季 |
  | 岩石灰 | `#a69a91` | 崖壁、礁石、山 |
  | 温润木 | `#9c6b42` | 码头、木构 |
  | 灯火金 | `#f8cd79` | 窗灯、灯塔、落成 |
  | 暮色橙 | `#e88e50` | 黄昏光 |
  | 雪色白 | `#dedcdd` | 积雪基色（阴影另配冷色） |

- **已实现。** `palette.ts` 分三层：`BOARD`（上表 10 色，B / C 期调色的目标，A 期不直接使用）；材质与物件族（`GROUND`、`ROCK`、`TREE`、`WOOD`、`STONE`、`PLASTER`、`GLASS`、`LAMP`、`GLOW`、`FESTIVE`、`FIGURE`、`GRANARY`、`LIGHTHOUSE`、各地标、`CULTIVATION`、`SKY`、`CUE`、`LABEL` 等），数值就是当前画面，每族注明归属的基础色；派生函数 `seasonGrass` / `seasonField`（季节）、`snowBlend`（积雪）、`decayRoof` / `decayWall`（衰败，B1 直接改这里）、`withAlpha` / `rgbOf`（透明度）。原来散在 `style.ts` 的 `SNOW`、`BEACH`、`WARM`、`SKIN`、`FIREWORK` 等也搬了进来。
- 昼夜的环境光关键帧仍在 `ambience.ts` 的 `dayLight()`，海的颜色仍来自主题变量 `--sea` / `--sea-deep`；这两处属于 C1 的分层调色，届时再并入调色板。

**A2 颜色迁移（不改观感）**
- 把 `terrain.ts`、`structures.ts`、`landmarks.ts`、`cultivation.ts`、`effects.ts` 里的颜色字面量改成调色板引用。
- 这一步**只重构、不调色**：用 4.1 的截图矩阵对比，像素差异应当为零或者肉眼不可见。真正调色放到 B、C 期。
- **已实现。** 上述五个文件之外，`render.ts`、`simulation.ts`、`paint/base.ts` 也一并迁移，共约 430 处字面量（含 rgba 与发光三元组）。迁移脚本逐处断言「替换后的调色板值 = 原字面量」，再用截图矩阵复核：60 张截图（含 `cover` 组）与改前**逐像素一致**。
- `tests/palette.test.ts` 守住原则 7：扫描 `src/island/` 下所有源码，除 `palette.ts`、`style.ts` 的 `MARKER`、`viewport.ts` 的主题变量回退值和 `utils.ts` 里 `shade()` 的黑白两端外，出现颜色字面量就失败。

**A3 截图矩阵**
- 按 4.1 节扩展 `island-shots.mjs`，补齐衰败场景（构造回溯日期的推进事实）和培育等级场景，跑出改前基线。

**A4 性能基线与真机复核**
- 用 4.3 节的方法记录 headless 基线。
- 在至少一台 iPhone（Safari 远程调试）和一台中端 Android（Chrome 远程调试）上测同一场景，确认第 1 节观察到的长帧在真机上是否存在。
- **headless 部分已完成（9.1 节）**：帧间让出 rAF 以后长帧基本消失，指向测量循环攒批光栅化；真机这一半需要有设备的人来测。

**A5 静态建筑层缓存（评估，必要时实施）**
- 树、山、房子、地标大部分帧不变，可以和地面一样画进离屏缓存。
- 难点是人物要和建筑按深度前后遮挡，可以考虑按深度分段缓存，或者只缓存「永远在人物后面」的部分。
- 先出评估结论（省多少、复杂度多高），再决定是否在 B 期之前做。如果 A4 证实真机有性能压力，就提前做。
- **已评估（9.2 节）**：B 期之前不做；海的静态部分放到 C3 一并缓存；实施整层缓存的触发条件写在 9.2 节。

**完成条件：** 调色板合并；A2 截图无差异；截图矩阵与性能基线记录在第 9 节；A5 有书面结论。

阶段的计算不变（一周安静、两周蒙灰、四周搬离；每有一天真实推进就回退一个阶段），只加强画面表现：

| 阶段 | 现在 | 目标（手机不放大也能分辨） |
|---|---|---|
| 0 正常 | 屋顶原色，窗灯约 90%，有炊烟 | 保持；广场铺地完整，生活道具（晾衣绳、花盆）齐全 |
| 1 安静 | 屋顶混灰 10%，窗灯约 50% | 屋顶饱和度明显降低；炊烟减半；广场边缘冒出草 |
| 2 蒙灰 | 屋顶混灰 45%，墙变暗，无炊烟，偶数户长杂草，井水变灰 | 村落地面整片褪色（以村中心为圆心的褪色区，画进地面缓存）；每户都有杂草；广场铺地缺块；生活道具减半 |
| 3 搬离 | 屋顶混灰 60%，单号户封窗，窗灯约 12% | 在 2 的基础上：有一户塌顶（剪影变化）；地面发黄；生活道具撤走；背包居民走向码头（已有） |

- 恢复时沿用现有的阶段转场（`stageCues`），不新增动画类型。
- 验收：4.2 节的盲看检查。
- **已实现。** 各阶段画什么集中在新的纯模块 `src/island/render/visual-state.ts` 的 `DECAY_LOOK`（`tests/visual-state.test.ts` 守住「一档比一档冷清、只减不增」）：
  - 屋顶先去饱和再混灰（`palette.ts` 的 `desaturate` / `decayRoof`）：安静时只保留约两成饱和度，八种村色都会变成灰调，手机上一眼和正常的村子分开；
  - 炊烟、夜灯按户的随机数和阶段比例取（`houseSmokes` / `houseLit`），安静时正好一半人家熄火；
  - 地面（进地面缓存，`groundKey` 加上了各村阶段）：广场石板边缘长草（安静起）、缺砖（蒙灰 3 块、搬离 5 块，`missingSlabs`，井底那块不算）；村里小路被草吃掉；以村中心为圆心的褪色区（`villageFade`，蒙灰灰褐、搬离枯黄，只盖地块顶面，积雪时淡一些）；
  - 蒙灰起每户门前都有杂草；院落生活道具只撤不换（正常、安静齐全，蒙灰隔一件撤一件，搬离全撤；撤掉的仍占着位置，道具不会挪到别家门口）；
  - 搬离时一户塌顶（`collapsedSlot`：挑一户封了窗的单号户，只有一户时就是它）：没有屋顶，只剩断墙、左后角一片残顶和几根椽子，剪影矮一截；`houseOutline` 同步给出塌顶的轮廓。

**B2 培育区 0–4 级**

等级规则不变（`src/logic/cultivation.ts`）。每一级都要在全景下多出一个看得见的元素；0 级要像「在等待」，而不是没画完：

| 区域 | 0 级 | 1 级 | 2 级 | 3 级 | 4 级 |
|---|---|---|---|---|---|
| 农田 | 翻好的空垄和田埂 | 嫩芽 | 半高作物 | 成熟，立稻草人 | 金黄，地头堆草垛 |
| 果园 | 树苗加支架 | 小树 | 成树 | 开花 | 结果，树下放果篮 |
| 鱼塘 | 石头岸边、芦苇、静水 | 睡莲 | 鱼影 | 鸭子与涟漪 | 小栈桥和钓竿 |
| 花园 | 篱笆围起的空花床 | 嫩芽 | 零星开花 | 成片开花 | 花拱门，蝴蝶 |

- 冬季各级都要有积雪版本（例如农田留茬、鱼塘结冰但保留岸边元素）。
- 新元素的点击说明沿用 `info.ts` 现有的培育区说明，不新增文字。
- **已实现。** `visual-state.ts` 的 `CULTIVATION_STEPS` 就是上表，`cultivationElements(kind, level)` 给出某一级画面上有哪些元素（长大的东西替换前一级：嫩芽 → 半高 → 成熟 → 金黄，树苗 → 小树 → 成树，开花 → 结果；其余元素一直保留），测试检查每一级都比上一级多一样新东西。`cultivation.ts` 按元素绘制：
  - 农田的作物先画一条条从上面看到的作物带，全景下就是「棕 → 嫩绿条 → 深绿 → 黄绿加稻草人 → 金黄加草垛」的颜色变化；
  - 果园四棵树：带支架和树坑的树苗 → 小树 → 成树 → 粉白的花 → 红果加果篮；
  - 鱼塘：石头岸、香蒲芦苇、静水的水光 → 睡莲 → 橙色的鱼 → 两只鸭子和涟漪 → 小栈桥与钓竿；
  - 花园：篱笆围起的抬高花床 → 嫩芽 → 几朵花 → 成片的花 → 正后方门口的花拱门（高出花床，衬着草地）与两只蝴蝶。
  - 积雪：田里是雪垄、冒头的麦苗、留茬、戴雪帽的稻草人和草垛；鱼塘结冰，睡莲和鱼影冻在冰下，鸭子守着冰洞，栈桥积雪；果园光秃，开花那一级的树干刷了白，结果那一级枝头挂着没摘的果子；花园只剩枯茎与籽头，疏密仍按等级。
  - 鱼、鸭子、蝴蝶、芦苇的动作在减弱动态效果时静止。遮挡 / 点击外框随等级变化（`cultivationExtent`：稻草人、成树、花拱门更高），不比原来的小。

**B3 粮仓**
- 改成一座仓房（石基、木墙、坡顶），门口的麻袋或草垛数量（0–5）对应可用时长的比例（`ratio`）。
- 比例低于 0.2 时仓门敞开、里面是空的，替代现在的警示色。
- 精确数字仍然在标签和说明卡片里；点击区域不小于现在。
- **已实现。** `drawGranary` 画成石基木板仓房、金黄草顶（和标记色 `MARKER.granary` 同一族），山墙朝右前方开大门。麻袋数 `granarySacks(ratio)`：五等分向上取整，有两成就至少一袋，满仓五袋；`granaryEmpty`：低于两成时仓门大开、里面黑洞洞空着，一袋不剩，不再用警示色。原来用「门半开」表示的「此刻正在用时间」（`granaryBusy`）改为山墙上的阁楼小门打开、吊杆吊着一袋，和余量互不相干（原则 3）。仓房轮廓 `granaryOutline` 并上原来圆仓的外框，既挡人也是点击范围：面积约为原来的 1.6 倍且包含原来的范围（此前粮仓的外框不带点击目标，只能靠地块就近判断和标签点开）。

**B4 村落识别与成长**
- 每座村落的广场插一面村色的旗；屋顶加瓦片线条；不同村落的墙面材质有差异（白灰、木板、石砌，按项目 id 哈希分配）。
- **待定决定 Q3**：村落满 10 间房以后，继续推进是否让房子升级（加二层、加院子）？如果定下来，需要在 `logic/` 里加一条纯函数规则并配测试，同时更新 README 里「每 3 块砖多盖一间房，最多 10 间」的说明。
- **已实现（识别部分；成长部分等 Q3）。** 井的左边插一面村色的旗（随阶段和屋顶一起褪色，减弱动态效果时不飘，算进井的遮挡轮廓）；墙面材质按项目 id 哈希分配白灰 / 木板 / 石砌（`wallMaterial`，墙色在 `palette.ts` 的 `WALL`，三档衰败各有一套）；四坡顶、双坡顶加瓦垄。瓦垄和墙面纹理是放大以后的细节：房子在屏幕上不足 26 CSS 像素时不画（`FINE_DETAIL`），全景下不添噪点，也省下每户几十段抗锯齿线的光栅化。

**完成条件：** 4.2 节盲看通过；`agenda-hit-smoke` 通过；性能在预算内。

### 5.3 C 期：光照、季节与海

**C1 分层调色**
- 用分层调色替换 `drawAmbient` 的整帧 multiply：
  - 海和天：黄昏往蓝紫走，夜晚往深海蓝走，**保持是蓝色的**。
  - 陆地和建筑：黄昏偏暖，朝西的立面加一点边缘光；夜晚降饱和、偏冷。
  - 阴影：黄昏和夜晚改用冷色。
  - 窗灯、灯塔、萤火、天灯继续用叠加发光，不受上面的调色影响。
- 地面缓存按调色结果重画，缓存键里的时间要量化（例如每 5 分钟一档），避免每帧失效。
- 在 `ambience.ts` 里给出各时段的目标色作为关键帧，配 vitest（关键帧单调、首尾连续）。

**C2 冬天**
- 积雪用「雪色白」打底，阴影用冷蓝色，保留雪堆的起伏。
- 处于正常或安静阶段的村落周围扫出路来（后果层，见原则 2）。冬天也能看出哪里活跃。
- 积雪时隐藏地块接缝线。

**C3 海**
- 从岸边的海水蓝到远处的深海蓝做明显渐变；把浅水圈加强到看得见。
- 沿岸加泡沫线。
- 画面上方加两三个远处小屿的剪影和云影（静态，画进缓存），填补空海。

**C4 随时间变化的阴影（可选）**
- 黄昏时阴影拉长并偏向东侧。成本高，放到最后，视性能余量决定。

**完成条件：** 黄昏、夜晚、冬天的截图对比通过评审；标签在各时段都清晰；性能在预算内。

### 5.4 D 期：地形与构图

**D1 草地**
- 在亮度噪声之外，再加一层低频的冷暖色相变化，形成草色斑块。
- 小花改成按季节变色、成簇出现：春天粉白，夏天黄白，秋天换成落叶色，冬天不画。去掉夏天像噪点的孤立白点。
- 放大后降低草丛的重复感：大小、密度、色相都有变化。

**D2 路网**
- 码头 → 粮仓 → 各村落 → 灯塔（档案馆）之间画土路，画进地面缓存。
- **待定决定 Q4**：路的磨损程度是否由数据决定？如果是，规则必须读后果层，例如「近 30 天这座村落确认做了的条目数」分 0–3 档。规则写成 `src/logic/` 里的纯函数并配测试，磨损档位进入地面缓存键。决定之前，路只画成固定样式。

**D3 地标基座**
- 每座地标加石台和台阶，再配两三件按类型挑选的道具（路灯、村色的旗、树、长椅），造型参照 `landmark-concepts.webp`。
- 基座要算进遮挡轮廓。

**完成条件：** 截图对比通过评审；地面缓存命中率不下降（平移、缩放之外不应失效）。

### 5.5 E 期：素材统一与质感

**E1 道具与建筑统一画风**
- **待定决定 Q1 / Q2**：先定目标画风和道具的处理方式（第 7 节）。
- 如果采用「后处理现有道具」：在 `scripts/slice-props.py` 里增加三步——
  1. 把颜色量化到调色板（含明暗档）；
  2. 减淡深色描边；
  3. 压低纹理细节。
  处理结果仍由脚本生成，不手改。
- 按缩放分级显示：道具在屏幕上的宽度小于约 14 CSS 像素时不画，或者换成简化的色块。
- 冬季变体：给道具叠一层程序化的积雪顶。`docs/art/README.md` 里「冬季积雪时整批不摆」的限制随之解除。

**E2 标签**
- 换成半透明、羊皮纸色调的胶囊，字号略小，和方向板一致。
- 培育区的「0/4」改成四个小圆点。
- **待定决定 Q5**：不放大时，村落标签是否只显示名字，人数和日程只在选中或悬停时显示？
- 继续使用 `label-layout.ts` 的避让和优先级。

**E3 纸纹与暗角**
- 运行时生成一张 256×256 的噪声纹理（不新增素材文件），以 3–5% 的强度 multiply 到画面上，再加轻微暗角。
- 结果画进缓存，暗色主题下降低强度。

**完成条件：** 近景截图里道具和建筑看起来出自同一画风；手机全景不再有杂乱小斑点；`docs/art/README.md` 同步更新。

### 5.6 F 期：高度起伏（需要先写 RFC）

- 目标：内陆台地高出半格，海岸崖壁高低不一，用台阶和坡道连接，参照方向板。
- 影响面：`iso()` 投影、点击判定与遮挡、人物寻路与落脚点、标签锚点、地面缓存、地图生成（`map.ts`，必须保证已有存档的地形和村落位置不变）。
- 在 A–E 稳定之后，先写独立的设计 RFC，评审通过再实施。本文只记录这一意图。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 改形状后点击判定或遮挡错位 | 原则 5：轮廓与绘制同源；每期跑 `agenda-hit-smoke` |
| 细节增多导致低端手机掉帧 | 原则 6 与 4.3 节预算；必要时提前做 A5 静态层缓存 |
| 地面缓存频繁失效 | 缓存键只放真正影响画面的输入；时间量化；在第 9 节记录命中情况 |
| 新视觉和已有符号含义冲突 | 原则 3；新增带含义的元素先在本文登记，再实现 |
| 截图不稳定，无法对比 | 一律通过 `island-shots.mjs` 的固定随机数和时钟产出 |
| 道具重新处理后体积增大 | 道具仍是按需加载的 webp；单张体积不超过现状的 1.5 倍 |
| 改动了已有存档的地形 | F 期之前不改 `map.ts` 的生成规则；F 期在 RFC 里单独论证兼容性 |

### 9.2 A5：静态建筑层缓存评估

**各类景物每帧的成本。** 原先的 `PERF_LAYERS=1` 把画景物的方法直接替换为空函数，连同夜间灯光登记也删除了，导致 `drawLights()` 少画光晕，因此把房子、树、地标等景物的缓存收益高估了。同时项目 / 人物 ID 不固定，跨运行的负载不可严格对比。旧表中夜间“静态”合计 76 ms（48%）/ 63 ms（61%）**已撤回，不再作为缓存决策依据**。

修复后的 `island-perf.mjs` 在加载页面前固定 `crypto.randomUUID`、`Math.random`，每次测量前恢复小人、模拟随机源、动效状态。进入图层测量时，它先**在计时区间外**完整绘制固定长度的帧序列，逐帧保存全部灯光登记（包括随时间变化的萤火虫）。之后对**完整绘制基线与每一个被省略图层**都使用同一个轻量 `drawLights()` 适配器，把对应时刻的完整灯光送入发光绘制；不在逐帧计时区间做逐项比较、数组复制或调用次数校验。这样非目标动态图层的灯光不会造成虚假的测试失败，发光成本与重放开销在两侧也一致。仅测量 `sky+lights` 时有意省略 `drawLights()`，因为该组本身包括发光层。**这些数字是跳过一组画法的理论成本上限**，仍可能包含未来缓存实现需要维护的少量灯光注册开销，不能直接当作最终缓存的实际收益。

**复测命令：** `PERF_LAYERS=1 node browser-tests/island-perf.mjs`（先构建并启动 Vite preview，详见脚本顶部）。2026-11-07 与第 9.1.1 节同一次运行测了桌面/手机、昼/夜四组。图层成本是「跳过该组绘制」的理论上限，百分比相对该轮带完整灯光适配器的整帧（桌面白天 101 ms、桌面夜晚 116 ms、手机白天 60 ms、手机夜晚 70 ms）。大约 1 ms 以内的差，包括测成负数的一行，视为噪声，不拿来估算收益。

| 旧记录（仅供追溯） | 桌面白天 | 桌面夜晚 | 手机白天 | 手机夜晚 |
|---|---|---|---|---|
| 整帧 +flush | 129 ms | 158 ms | 82 ms | 103 ms |
| “静态”六类，旧算法合计 | 55 ms / 43%（待复测） | ~~76 ms / 48%~~（无效） | 43 ms / 52%（待复测） | ~~63 ms / 61%~~（无效） |
| 修复后同负载复测（2026-11-07） | 38 ms / 38% | 43 ms / 37% | 28 ms / 47% | 32 ms / 46% |
| 其中海 `drawSea` | 32 ms / 32% | 33 ms / 28% | 13 ms / 22% | 13 ms / 19% |

**「静态」并不都静止。** 逐个检查绘制函数里用到动画时钟的地方：每棵树每帧随风摆动（`drawTree`），房子带炊烟和节日灯笼（`drawHouse` / `houseFestival`），风车转帆、地标的旗子飘、纪念塔的火焰跳、灯塔光柱转、钟楼指针按时刻走；夜里这些景物还要往 `lights` 里登记灯光位置；即使缓存静态几何，动态光晕仍须绘制。真正一帧不变的只有山、井（节日之外）、粮仓（存量过渡之外）和道具。

**三种做法：**

1. **按深度分段缓存。** 小人和景物按深度（i + j）交错绘制，小人一走动，分段边界就要重切，缓存频繁失效。不推荐。
2. **整层缓存 + 补画前景。** 静态景物（去掉动画部件）按原顺序画进一张离屏图；每帧贴图、画小人，再把「深度在小人之前、轮廓压到小人」的景物裁剪到小人的外框里补画一遍（现成的 `occluders` 轮廓正好能判断）。需要：把炊烟、旗、帆、火焰、光柱从景物绘制里拆成每帧单独画；树要么放弃摆动、要么继续每帧画；缓存键包含视口、季节、积雪、天气、昼夜点灯、各村房数与阶段、地标、节日、选中状态；夜里的灯光位置随缓存一起存。候选包括房子、山、地标、井 / 粮仓 / 灯塔、道具；**原“可省 25–45%”估计已撤回**，要待灯光成本保留后的重测结果才能给出可信占比；树另计。改动面大，要配套截图与点击回归。
3. **先缓存海的静态部分。** 海占整帧的 18–30%，但其中背景渐变和两圈浅水（每块海岸地块一组椭圆）每帧都一样，只有浪花、远处波纹和波光在动。海在所有景物后面，没有深度遮挡问题，缓存键只要视口、主题、天气。成本低、收益接近做法 2。

**临时结论（2026-11-02）：B 期之前不做静态建筑层缓存，待修复后的基线和真机复核后再确认。**

- 修复前 4× 降速下 step+draw 中位数 22–29 ms，在 33 ms 的帧预算内，但当时负载并不完全可重复。第 9.1.1 节重测后，桌面 4× 的 step+draw 中位数是白天 16 ms、夜晚 18 ms，仍低于 33 ms。这次 headless 重测没有触发做法 2。真机确认仍待做。
- C3 改海的时候顺手做做法 3（海的静态层进缓存）。2026-11-07 的海约占整帧 +flush 的 19–32%，和原先「18–30%」的判断同级。
- 出现以下任一情况再实施做法 2：真机复核时中端 Android 的空闲帧中位数超过 33 ms；或者后续加细节后，桌面 4× 的 step+draw 中位数超过第 9.1.1 节基线的 110%（白天 17.6 ms、夜晚 19.8 ms）。
- B1 新增的村落褪色区按计划画进地面缓存，`groundKey` 要加上各村的衰败阶段。
